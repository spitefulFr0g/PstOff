# PstOff

PstOff is an MIT-licensed OST-to-PST converter under construction. The engine
and CLI build on Linux; the GUI is a Windows-only skeleton. No working
conversion or supported-format claim is made by this foundation. `inspect`
and `convert` currently return `NotImplemented`, except pre-cancelled work.

## Prepare and check

Install Rust 1.82 or newer with `rustfmt` and `clippy`, and Linux `bubblewrap`.
Use a toolchain that supports the committed lockfile's dependencies (the
foundation was checked with Rust 1.99.1). From this repository:

```sh
CARGO_HTTP_USER_AGENT='PstOff-research (https://github.com/spitefulFr0g/PstOff)' cargo fetch --locked
scripts/check
```

Fetch downloads dependencies without executing crate code. Every build and
test, including the first one, must use `scripts/cargo-sandboxed`; it removes
network and home access, mounts source read-only and permits only target and
temporary writes. Use host `rustfmt` to apply formatting; the sandbox runs its
read-only check. `scripts/check` checks dependency licenses/pins, formatting, Clippy and engine/CLI/GUI
skeleton tests. It does not execute the imported fork's upstream tests or
build GPUI. It is the maintained Linux CI entry point. A missing sandbox,
component, dependency, or user namespace is a failure, never a skipped check.

```sh
scripts/cargo-sandboxed test --locked -p pstoff-engine
scripts/cargo-sandboxed run --locked -p pstoff-cli
```

Windows builds need explicit permission under [safety](docs/agents/safety.md).
The GUI has no GPUI dependency until its Windows feasibility task selects and
audits a pin; Linux resolution and compilation do not include GPUI. The
skeleton exits with failure and clearly states its status.

## Architecture and tests

`pstoff-engine` owns the platform-neutral `inspect`/`convert` seam and typed
outcomes, shared by both frontends. Format code stays behind that seam.
`third-party/pstfree` is the MIT upstream base imported at
`b6e2ff31592f74458f0481d4671251c92044d8f0`, with only its library sources and a
PstOff manifest; it is not a copy of the experimental writer spike. Reader
and writer tasks own its subsequent adaptation. The engine normally depends
on Microsoft's unmodified `outlook-pst` at
`cfb721daee538acc50d2bad6faac5ce724f6037d` for allocation maps and independent
readback. Direct registry versions are exact and all transitive versions are
locked. See [dependency notices](THIRD-PARTY.md).

Integration tests in `crates/engine/tests` import only the engine public API
and independent reader. The support module creates generated bytes in a fresh
sandbox temporary directory, cleans them up and never discovers fixtures by
walking the checkout. The initial negative case verifies unchanged source,
no outputs and explicit unavailable status; it does not prove format rejection.
An independent-reader negative control demonstrates wiring, not a successful
PST roundtrip. Subsequent reader/writer tasks must add supported generated OSTs
and positive readback assertions for hierarchy, counts, properties, recipients,
attachments and embedded messages, matching each difference to the report.

Public fixture additions require a documented immutable URL/revision, SHA-256,
license and generation/source description. Download into a fresh `/tmp`
directory with the research User-Agent, review before use and never execute
downloads. Prefer reproducible synthetic fixture generators. Tests must take
explicit public/generated paths; never accept an environment-controlled path
or glob into `testdata/private`. Do not commit mail content, even from public
fixtures. Committed evidence contains only structural IDs, counts and hashes.
No public mail fixture is downloaded by the full-check command.

Positive readback, strict SCANPST, libpff comparison, Windows portable builds,
and human Outlook and GUI checks remain required later acceptance gates.
See [Faithful checks](docs/agents/faithful-checks.md). Linux foundation checks
cannot establish Faithful conversion or Windows deployment.
