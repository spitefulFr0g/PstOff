# What an OST can reveal about a Partial cache

Research for [#5](https://github.com/spitefulFr0g/PstOff/issues/5), under [#1](https://github.com/spitefulFr0g/PstOff/issues/1). 2026-10-21. Planning only; no converter implementation or private mailbox inspection.

## Answer

**Sometimes an OST can positively identify an item marked as headers-only, or show that locally referenced data cannot be read. It cannot certify that it contains the whole Mailbox.** Items outside a sync window can remain exclusively on the server, with no local item to inspect. The documented sync-window setting lives in the Outlook profile/Windows registry, not in a documented universal OST completeness field. [Microsoft's sync-window explanation](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/only-subset-items-synchronized)

Recommended v1 decision: always report **Mailbox completeness: unknown** for an OST-only Conversion. Add specific evidence when found; absence of a warning must never become a completeness claim. Keep three questions separate: what the file marks as partially downloaded; what local data the reader could read; and how much of the server Mailbox was ever cached. This separation is a design inference from the evidence below.

## Evidence and its limits

### 1. A documented headers-only item marker

**Verified semantics:** `PidLidHeaderItem`, alias `dispidHeaderItem`, is a named property in `PSETID_Common` (`{00062008-0000-0000-C000-000000000046}`), numeric LID `0x00008578`, type `PT_LONG` / `PtypInteger32` (`0x0003`). Microsoft describes it as distinguishing header-only from header-and-body downloads in Cached Exchange Mode. Microsoft's sample treats a successfully read, correctly typed **nonzero** value as headers-only. [Canonical property](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidlidheaderitem-canonical-property), [Microsoft's sample, pinned source](https://github.com/MicrosoftDocs/office-developer-client-docs/blob/eedbd61ca40689e7cfed5e1cfd9440a9dc3ab7a5/docs/outlook/mapi/how-to-determine-if-outlook-downloaded-only-the-header-of-a-message.md), [GUID definition](https://github.com/MicrosoftDocs/office-developer-client-docs/blob/eedbd61ca40689e7cfed5e1cfd9440a9dc3ab7a5/docs/outlook/mapi/mapi-constants.md)

**On-disk interpretation:** if the reader resolves that property through the file's name-to-ID map and reads a nonzero integer, report “item marked as headers-only.” `0x8578` is the **LID**, not a universal property ID/tag to search for in every message. Named properties receive store-specific property IDs; MS-PST describes the map and the assigned ID calculation in §§2.4.7–2.4.7.3. [MS-PST specification](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/), [Microsoft's sample resolves names before reading](https://github.com/MicrosoftDocs/office-developer-client-docs/blob/eedbd61ca40689e7cfed5e1cfd9440a9dc3ab7a5/docs/outlook/mapi/how-to-determine-if-outlook-downloaded-only-the-header-of-a-message.md)

**Unknown coverage:** these sources document Outlook/MAPI behavior, not mandatory persistence of that property in every OST variant, provider, or Outlook build. No raw-file fixture has been checked here. A raw property found with the documented identity is meaningful positive evidence; a missing map entry, absent property, zero value, unreadable property, or unsupported file variant does not prove that all payloads or all Mailbox items are present. Do not copy the sample's “false on any failure” behavior into a completeness verdict.

**Do not invert the values:** Outlook's object-model `MailItem.DownloadState` uses `OlDownloadState`: `olHeaderOnly = 0`, `olFullItem = 1`. That is an API enum, not evidence of a stored property with the same encoding. Do not use it as the value definition for `PidLidHeaderItem`. [DownloadState](https://learn.microsoft.com/en-us/office/vba/api/outlook.mailitem.downloadstate), [enum](https://learn.microsoft.com/en-us/office/vba/api/outlook.oldownloadstate)

### 2. Exchange remote-header and status fields: candidates, not universal detectors

**Verified disk schema:** MS-PST §2.4.8.6.2.1 includes `PidTagExchangeRemoteHeader`, alias `PR_EXCHANGE_REMOTE_HEADER`, property ID `0x0E2A`, `PtypBoolean` (`0x000B`), full tag `0x0E2A000B`, in the **search-folder contents-table template**. The description is “Has Exchange Remote Header.” Crucially, this template has **no data rows**: column existence alone is not evidence of a partially downloaded item. [MS-PST table schema](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/cdcf9571-049f-47f5-b075-8374057134ec), [MFCMAPI alias definitions](https://github.com/microsoft/mfcmapi/blob/2c59cc71512c56393671738690fa1c88db2a4d1f/core/interpret/genTagArray.h)

**Inference/unknown:** retain an actual true item/row value as an Exchange remote-header diagnostic, but validate its relationship to missing bodies against fixtures before making it a primary v1 detector. The cited specification does not establish universal OST persistence, IMAP applicability, or a mailbox-wide completion guarantee. Avoid counting search rows as additional items: search views can repeat items.

`PidTagMessageStatus` / `PR_MSG_STATUS` is `0x0E17`, `PT_LONG`, tag `0x0E170003`. Microsoft explicitly describes it as a contents-table column whose value can differ between instances, rather than an ordinary message property. Its `MSGSTATUS_REMOTE_DOWNLOAD` and `MSGSTATUS_REMOTE_DELETE` states mean **marked for an action** against a remote store. They are not a general “body is absent” or “mailbox is complete” bit. `PidTagMessageFlags` / `PR_MESSAGE_FLAGS` is a separate `0x0E070003` property; its attachment flag is also not a completeness flag. [MessageStatus](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagmessagestatus-canonical-property), [MessageFlags](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagmessageflags-canonical-property)

**IMAP:** Microsoft documents that opening a message through a wrapped IMAP store can trigger a full-message download; unwrapping permits access to its current state. This establishes that partially downloaded IMAP items exist, not which universal flag must be persisted in an IMAP OST. The documented `PidLidHeaderItem` contract above is expressly Cached Exchange Mode. Treat IMAP detection coverage as unverified until raw IMAP fixtures establish a marker; apply payload diagnostics independently. [Microsoft IMAP proxy-store documentation](https://github.com/MicrosoftDocs/office-developer-client-docs/blob/eedbd61ca40689e7cfed5e1cfd9440a9dc3ab7a5/docs/outlook/mapi/iproxystoreobject-unwrapnoref.md)

### 3. Sync window: profile fact; age distribution: heuristic

**Verified external setting:** `SyncWindowSetting` and `SyncWindowSettingDays` are registry settings; the former expresses months, with `0` meaning All. Microsoft documents policy configuration under `HKEY_CURRENT_USER\Software\Policies\Microsoft\Office\16.0\Outlook\Cached Mode` and says the active setting is maintained in profile settings. A policy key is not itself proof of what one historical OST actually downloaded. [Microsoft's shared-folder/profile explanation](https://learn.microsoft.com/en-us/outlook/troubleshoot/data-files/fewer-emails-in-shared-mailboxes-or-public-folders)

**Not established on disk:** no cited primary source establishes a stable OST property that recovers the effective slider, its history, or a completed-sync-to-that-setting guarantee. Do not invent a property ID, decode opaque sync blobs by guesswork, or assume a property described in an Exchange synchronization protocol is necessarily persisted in the cache.

**Inference:** a sharp cutoff in local message delivery dates across mail folders can suggest a sync window. It also fits a recently created Mailbox, retention/deletion, archiving, or selective activity. The oldest item does not reveal the slider or the number of missing items. Microsoft says the mail slider does not control several nonmail folders, including Calendar, Contacts and Tasks; an old appointment cannot disprove a recent-mail cutoff. [Sync-window behavior and exceptions](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/only-subset-items-synchronized)

### 4. Folder counts: local consistency, not a server denominator

**Verified:** `PidTagContentCount` / `PR_CONTENT_COUNT` has ID `0x3602`, type `PT_LONG`, tag `0x36020003`. It is computed by the message store and excludes folder-associated entries. `PidTagContentUnreadCount` / `PR_CONTENT_UNREAD` is `0x36030003`; unread count is a different quantity. MS-PST §§2.4.4.1.1–2.4.4.3 also describe folder counts and duplicated table/object properties. [ContentCount](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagcontentcount-canonical-property), [unread count](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagcontentunreadcount-canonical-property), [MS-PST](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/)

**Inference:** compare stored counts with enumerated ordinary local items, accounting for associated items and search folders. A discrepancy is a local consistency/readability diagnostic: damage, unsupported parsing, stale metadata, and partial synchronization remain possible explanations. Equal counts merely agree about the represented local store; they supply neither a current server count nor a list of never-cached folders. No reliable, universally persisted server-total property was established in this research. Never label a count difference “N messages missing from the Mailbox” without a validated independent denominator.

### 5. Shared/public folders and Online Archive: presence has narrower meaning than absence

**Verified:** Outlook 2016 and later can apply the mail sync window to shared mailboxes and public-folder favorites when their download settings are enabled. Microsoft documents separate controls and a `DisableSyncSliderForSharedMailbox` override. Thus a visible shared/public folder can itself be a Partial cache. [Microsoft's shared/public synchronization documentation](https://learn.microsoft.com/en-us/outlook/troubleshoot/data-files/fewer-emails-in-shared-mailboxes-or-public-folders)

**Verified:** an Online Archive is an additional mailbox. Microsoft documents that Outlook accesses the archive online and does not create a local copy even in Cached Exchange Mode. [Exchange archive client access](https://learn.microsoft.com/en-us/exchange/policy-and-compliance/in-place-archiving/in-place-archiving#client-access-to-archive-mailboxes)

**Inference:** an OST can show folders/items actually represented in it, but cannot enumerate all uncached shared mailboxes, public folders, or an Online Archive from their absence. Report those as possible exclusions, not “missing archive detected.” A normal folder named Archive is not evidence of an Online Archive mailbox. Profile/server access would be needed to establish the full accessible-store inventory; it is outside PstOff's scope. Even an otherwise complete primary Mailbox cache need not include the user's other mailboxes.

### 6. Missing payloads: report the observed defect and preserve the uncertainty

**Verified property vocabulary:** bodies can have plain-text `PidTagBody` / `PR_BODY` (`0x1000001F` Unicode, `0x1000001E` ANSI), HTML `PidTagHtml` / `PR_HTML` (`0x10130102`), or compressed RTF `PidTagRtfCompressed` / `PR_RTF_COMPRESSED` (`0x10090102`). Absence of just `PR_BODY` is insufficient to say there is no body. [Body](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagbody-canonical-property), [HTML](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtaghtml-canonical-property), [RTF](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagrtfcompressed-canonical-property)

`PidTagAttachMethod` / `PR_ATTACH_METHOD` is `0x37050003`. By-value attachments use `PidTagAttachDataBinary` / `PR_ATTACH_DATA_BIN` (`0x37010102`); embedded messages use `PR_ATTACH_DATA_OBJ` (`0x3701000D`). Reference/web-reference attachments can legitimately keep content outside the message. Attachment method and payload properties are not automatically kept consistent by the store. [AttachMethod](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagattachmethod-canonical-property), [binary data](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagattachdatabinary-canonical-property), [object data](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagattachdataobject-canonical-property)

**Inference:** an unreadable referenced block, missing required by-value payload, or attachment flag/table disagreement warrants a diagnostic. A blank body can be legitimate; a reference attachment is not proof of incomplete caching; corruption and reader limitations can resemble missing downloads. Report exact observations and error categories, not an inferred server-side cause. An external attachment reference is also distinct from an item that was never cached.

## Proposed Conversion report language and decisions

Use these as proposed product text, not verified statements about a particular input:

- Always: **“Mailbox completeness could not be verified. This PST contains data readable from the selected OST folders. Older items, uncached folders, and other mailboxes may be absent. No partial-cache warning does not prove that the OST contains the complete Mailbox.”**
- Positive marker: **“N items are marked as headers-only in the OST. Their full contents may not be available for Conversion.”** Count unique source items, attach local identifiers and the observed marker/value to report details, and distinguish preserved headers from Skipped items.
- Payload issue: **“N attachment payloads could not be read from the OST. The report lists affected items and read errors; the cause could not be determined.”** Use a separate message for external references whose contents are outside the OST by design.
- Optional heuristic: **“The cached mail has a recent-date cutoff. This may reflect an Outlook sync window; the setting and amount of uncached mail could not be determined.”** Do not enable this warning until a bounded, documented rule avoids noisy guesses.
- No positive marker: **“No supported headers-only markers were found. This does not verify Mailbox completeness.”** If inspection failed, say **“Headers-only marker inspection was incomplete”** and give the reason instead.

Recommended next decisions: (1) require the unconditional completeness statement; (2) support the mapped `PidLidHeaderItem` positive diagnostic after fixture validation; (3) keep heuristics optional and separate from read failures; (4) keep Mailbox completeness independent of Faithful Conversion of the available source; (5) never promise to recover data that was not cached.

## Remaining uncertainty and a bounded validation task

The semantic question is answered; universal raw-OST detector coverage is not. Validate with small synthetic fixtures containing no personal data: full and headers-only Exchange caches, a limited-window Exchange cache, an IMAP headers-only cache, and an external-reference versus by-value attachment. Inspect copies offline for the named-property mapping, actual item values, table values, and readable payloads; compare against creation settings without changing the files. Include an item outside the window to demonstrate that there need not be a local placeholder. Record Outlook/provider/file versions. This is proposed follow-up work, not work performed here.

Research reused existing Microsoft documentation/specification copies and MFCMAPI sources and checked Microsoft web pages. No downloaded code was executed, no model worker was launched, and no implementation or private test data is included. All evidence above is first-party Microsoft material; raw-file conclusions are explicitly limited where only API/schema documentation exists.
